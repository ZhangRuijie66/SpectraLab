## 🔧 导出口径三分裂 → 单一来源

### 同一份数据，GUI 与命令行导出的图分辨率差 2–4 倍

- **现象**：审计实测同一批数据的两条导出路径产物 DPI 完全不同：
  ```
  GUI（导出当前图）              600 dpi
  plot_absorption  CLI           200 dpi
  plot_emission    CLI           200 dpi
  plot_3d_scan     CLI           200 dpi
  plot_compare     CLI           300 dpi
  plot_lifetime.summary          200 dpi   （1377×1774 px，投稿会被退）
  plot_lifetime.export_report_pdf 150 dpi
  ```
  用户把 GUI 出的图和命令行出的图放进同一份报告，肉眼就能看出不齐。
- **根因**：这个值在**六处各写了一份**，从来没有单一来源。
- **修复**：新增仓库根 `export_defaults.py`（`EXPORT_DPI_DEFAULT=600` /
  `EXPORT_DPI_VECTOR_MIN=300` / `EXPORT_DPI_PREVIEW=150`），
  `gui_config.py` 从它转出供 GUI 使用；五个 `plot_*.py` 的 `dpi=` 默认值
  全部改为 `None`，在 `savefig` 处回落到共享口径。根目录脚本仍能脱离 GUI
  目录单独运行（`import` 失败时退回字面量）。
- **验证**：回归项「导出 DPI：GUI / CLI / 汇总图读同一口径」逐个模块断言
  `mod.EXPORT_DPI_DEFAULT == export_defaults.EXPORT_DPI_DEFAULT`，并用
  `inspect.signature` 检查 5 个关键函数的 `dpi` 默认值**必须是 None**
  （防止将来又被改回硬编码）。

## 🔧 峰表：图上明明有数字，程序从不产出峰位/峰高表

- **现象**：勾选「标记峰」后画布上有 `548`、`564` 这些标注，但整个程序
  **没有任何地方产出峰位/峰高表**（全仓 grep `peak_table` / `峰表` 零命中）。
  用户只能用眼睛抄，或改用「积分结果」表间接推——那是另一个口径
  （积分边界不是峰位），推出来的数不对。
- **根因**：`find_absorption_peaks` / `find_peaks` 返回的
  `peak_wavelengths` / `peak_intensities` 在 `_plot_*` 里**用完即弃**。
- **修复**：画峰的同时记录到 `self._last_peaks`，「导出」菜单新增
  「导出峰表（CSV / XLSX）」，附「相对峰高」列（以本表最大峰为 1）。
  6 个绘图点全部接入（合并图 / 单图 / 差谱 / 发射合并 / 发射单图）。
- **口径一致性**：只记录**真正画出来的**峰——被「条数多时只标最强曲线」
  规则裁掉的峰不进表。否则「表和图对不上」比没有表更糟。
- **同时修复的一类老问题**：`_invalidate_results()` 此前漏了峰表，
  换文件夹后导出会写出上一批数据的样品名（与 v4.44 修过的那批
  `_last_*_result` 是同一类问题）。

## 🔧 寿命结果 JSON：149 KB 里 99% 是可重读的原始数组

- **现象**：单个样品的 `*_fit_result.json` **149 KB**，其中 `time`/`decay`
  各 4000 点原始测量数据（能从源文件重读），`info` 里还塞着 `y_fitted` /
  `residuals` / `irf_shifted` 三条同长度曲线。批量 20 个样品 = 3 MB 纯冗余，
  而真正的结论字段只有几十个。
- **修复**：拆成两个产物
  - `*_fit_result.json` —— 只留结论（τ、占比、χ²R、拟合区间…），
    τ 分布抽稀到 ≤200 点保留形状；
  - `*_curve.csv` —— 曲线（time / decay / irf / irf_shifted / y_fitted /
    residuals），Excel 直接可读，想复核拟合质量的人用它。
  json 里用 `_curve_file` 指过去，并写 `_note` 说明。

## 🎨 荧光寿命图：时间轴 78% 是噪声地板

- **现象**：Ce6 数据时间轴 0–399 900 ns，而拟合只用到通道 233–894
  （23 300–89 400 ns）。图上**右侧 78% 的面板全是平的噪声地板**，
  衰减曲线被挤在左边不到 1/4，IRF 峰只剩一条竖线。
- **修复**：主画布按拟合区间裁剪 xlim（前留 15%、后留 40%，各至少 20 点），
  并把拟合窗口画成浅色 `axvspan` 阴影带——不看诊断页也知道哪一段参与了拟合。
- **验证**：回归项用 4000 点、通道 233–894 的合成数据断言
  「时间轴跨度 < 全长 75%」且「完整包含拟合区间」。

## 🎨 拟合诊断页：上图 xlabel 与下图 title 间距 0 px

- **现象**：上图 `Time (ns)` 的 bbox 是 y=(239,255)，下图标题的 bbox 是
  y=(222,239)——**间距 0 px**，两行字上下紧贴，读起来像一句乱文。
  下图标题还很长（带「→ 越多说明残差越有结构」），宽度接近整张画布。
- **修复**：`hspace` 0.35 → 0.55；上图去掉 xlabel（它的标题已说明内容，
  横轴量纲由下图承担）；下图标题缩短，判读口径移到 xlabel。

## 🎨 拟合诊断页：「拟合起点 / 拟合终点」两个标注糊成一句话

- **现象**：两个标注是按「数据坐标 + 轴分数」混合定位的，各自贴在自己的
  竖线旁。但拟合区间相对全长往往很窄（实测 233–894 ch 落在 0–400 000 ns
  上，只占左边 22%），两个 4 字标注**相向生长**（一个左对齐向右伸、
  一个右对齐向左伸），于是挤成「拟合起..合终点」读不出来。
  实测两个 bbox：`x=[154,204]` 与 `x=[198,248]`，横向重叠 6.5 px、
  纵向完全重合。
- **修复**：按「拟合区间跨度占全时间轴的比例」判断是否错开——小于 35% 时
  把「拟合终点」下移一档（0.94 → 0.80）。**判据特意不用像素换算**：
  出图前画布还没拿到真实尺寸，`transData` 算出的像素距离不可靠
  （实测同一段代码手算 104 px、draw 后仍是 104 px，却给出了相反判定）。

## 🎨 寿命主图纵轴跨 19 个数量级（既有缺陷，本次一并修）

- **现象**：主图纵轴范围是 `1 – 5.97e19`，跨 19 个数量级——衰减曲线被压成
  一条贴在 10³ 的直线，整个寿命图根本读不出来。
- **根因**：IRF 是高斯型，两翼会衰减到 ≈0 的**正数**；log 轴自动缩放在
  「下限被 `set_ylim(bottom=1)` 钉死 + 数据趋近 0」的组合下会推出荒谬的上界。
  最小复现（三个量单独画）：
  ```
  只画 decay 散点          ylim = (1, 5.94e+03)   ✔
  只画 y_fitted 线         ylim = (1, 2.88e+03)   ✔
  只画 IRF 线              ylim = (1, 5.37e+19)   ✘ ← 元凶
  三条全画（实际实现）      ylim = (1, 5.97e+19)
  ```
- **修复**：显式设上限 = 所有曲线最大值的 3 倍（实测收到 `1 – 12607`，
  跨 4 个数量级，IRF 峰与衰减曲线清楚分开）。
- **说明**：这条在 v5.0.1（HEAD）上**同样存在**，不是本版引入。
  之所以现在才发现，是因为一并做了「时间轴按拟合区间裁剪」——裁掉右侧
  大片噪声地板后纵轴问题才显出来。这也说明**改动会暴露相邻的既有缺陷**，
  修完一个视觉问题要重新看图、不能只看断言。

## 🎨 寿命图颜色：浅色/打印友好主题下对比度只有 1.74–3.09:1

- **现象**：`#66ccee`（散点）对白底 **1.84:1**、`#ccbb44`（IRF）**1.95:1**、
  `#4ade80` **1.74:1**——远低于图形元素 3:1 门槛，浅色与打印友好主题下
  散点和 IRF 几乎隐形。而高对比主题的存在意义就是打印可读。
- **根因**：这些颜色只按「深色够亮」挑过，且诊断页的判据是
  `theme == 'dark'` **二分支**——仓库有三套主题，contrast 走的是 light 分支，
  但它需要的对比度比 light 更高，二分支根本表达不出来。
- **修复**：新增 7 个主题令牌 `MPL_LIFE_DATA` / `_IRF` / `_IRF_RAW` /
  `_FIT` / `_MARK` / `_ACF` / `_CI`，三套主题各给一组（全部 ≥4.5:1）；
  contrast 主题全部取纯黑/深色，黑白打印后靠线型仍能区分。
- **验证**：回归项断言三套主题都齐全、对 `MPL_AX` 底色 ≥ 4.5:1，
  且**三套之间取值互不相同**（防止忘了按主题给、改了个寂寞）。

## 🎨 寿命分布 τ 轴：4 个数量级里 99% 的质量只占 0.16 个

- **修复**：按分布质量的 0.2% / 99.8% 分位裁 xlim（各放宽 2 倍），
  最多仍保留原始网格范围。

## 🎨 IRF 平移量 `2.2e+03` → `1,499`

- 原来用 `:.2g`，`1499 ns` 被格式化成科学计数法。这是给人看、给人抄的参数。
  新增 `_fmt_shift()`：≥1000 用千位分隔、≥1 用 3 位有效数字。

## 🎨 峰标注：关闭「峰位标数值」后仍留 6 个空 Text 对象

- **现象**：`_peak_label` 在未勾选时返回空串，但调用方**仍无条件**
  `ax.annotate('')`。实测每次重绘在图里留 6 个空 Text——肉眼看不到，
  但它们参与 bbox 计算、导出时被序列化，还让「自动避让重叠标注」类逻辑
  失效（空串的 bbox 是退化矩形，避让算法把它当成占了位置的标注）。
- **修复**：新增 `_annotate_peak()`，标签为空时**根本不创建对象**；
  10 处调用点全部替换。
- **验证**：回归项断言关闭后 `ax.texts` 里空串数量为 0，**同时**断言打开后
  确实标出了数字（防止为了不建空对象把功能一起关掉）。

## 📊 数据比较：同浓度重复点被连成"假趋势"竖线

- **现象**：05 数据 12 个点只落在 3 个 x 值上（x=10 有 6 个、20 有 3 个、
  50 有 3 个）。`ax.plot` 把这些同 x 的点按**读入顺序**串起来，在图上画出
  一条条**竖直的"假趋势"**，看起来像数据在剧烈跳动，实际只是重复测量离散。
  而且没有误差棒——x=10 组标准差高达 51%（11707±5935），图上完全看不出。
- **修复**：有重复测量时改为「均值 ± 标准差」误差棒（capsize=3），原始点
  以 35% 透明度叠在均值位置（不丢信息）；`summary` 增加 `aggregated`
  字段报告重复次数。无重复测量时保持原来的折线不变。

## 📊 数据比较：纵轴 10⁵ 量级时 tick 是 6 位数

- 峰面积最高到 3.8×10⁵，原图 tick 直接写「383400」。改为
  `ScalarFormatter(useMathText=True)` + `powerlimits=(-3,4)`，顶部显示 ×10⁵。

## 📊 数据比较：空图路径不恢复边距

- **0 点分支**只 `set_axis_off()`，没有 `subplots_adjust`——`MplCanvas` 初始
  边距是 0（提示文字铺满用），于是 xlabel/ylabel/title 全被算到画布外，
  实测越界 `top +23px`、`left −51px`。已补回正常边距。

## 🧪 测试自身的两处缺陷（本次一并修）

### 1. `t_gui_window_lifecycle` 的基准里混着前序检查项的遗留

原断言取 `allWidgets()` 的**绝对值**做基准（`left < base // 4`）。这个 base
里混着前面几十个检查项留下的、还没被 GC 回收的窗口。一旦新增检查项让遗留量
跨过某个阈值，`_make_gui()` 内部会恰好触发一轮 GC 把这些遗留一次性收走——
**base 反而变小**（v5.0.2 加 4 条 GUI 检查项后 base 从 2881 掉到 1093），
`base//4` 随之压到 273，被固定的 646 个残留判为失败。

关键观察：**泄漏量一点没变**（HEAD 与本版的 `left` 都是 646），
变的只是测量起点。现改为**增量式**：只问"这个窗口自己建的控件回收掉了吗"
（`freed >= built * 0.9`）。

> 顺带记下一条既有事实：每个 `AbsorptionGUI` 实例 GC 后仍留 19 个控件
> （光谱减法组的 QLabel/QComboBox/QCheckBox 及其 QListView 容器），
> HEAD 同样如此，不是本版引入。数量恒定，不随建/销毁次数增长。

### 2. 新增的 xlim 测试用错了点数

审计原文的通道号 233–894 是 **4000 点**数组上的下标（dt=100 ns，
ch233=23 300 ns、ch894=89 400 ns）。我第一版用了 1000 点，同一组通道号
只占 66% 宽度，测不出"78% 噪声地板"这件事，报了个假失败。
